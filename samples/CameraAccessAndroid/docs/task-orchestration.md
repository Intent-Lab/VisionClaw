# Gemini 판단을 활용한 실시간 작업 관리 설계

상태: 제안 설계. 2026-09-19에 핵심 작업 관리 로직을 구현했다. 실제 적용 범위·검증·제한은 [변경 내역](2026-09-19-task-management-changes.md)을 기준으로 확인한다. 이 문서 전체가 구현됐다는 의미는 아니다. 기존 Gemini Flash의 의도 판단과 도구 선택을 유지하고 앱에 작업 상태·실행 정책을 추가한다. 별도의 발화 분류 모델이나 모든 명령 앞의 추가 LLM 호출을 기본 경로로 넣지 않는다.

## 책임

- Gemini: 새 발화가 기존 요청의 계속/정정/대체/취소/추가/결과 문의인지 판단하고 대상 작업을 선택한다. "그거"나 "응"의 대상이 둘 이상이면 확인한다. 완료 여부를 추측하지 않는다.
- 앱: 작업 ID 발급, 변경 버전 검사, 승인 범위, 자원 충돌, 실제 중단 가능 여부, 결과 소유권, 중복 실행, 시간 제한, 상태 보고를 통제한다.
- 도구 어댑터: 카메라/HTTP/화면 실행 등 각 기능의 시작·취소·상태 조회를 제공한다. 물리 동작의 중단을 보장할 수 없으면 결과를 분리하고 사실대로 보고한다.

대화의 현재 관심 작업과 실제 실행 중인 작업은 다르다. 관심이 검색으로 옮겨가도 명시적으로 유지한 녹음은 계속될 수 있다.

## 식별자와 상태

| 항목 | 역할 |
|---|---|
| session_generation | 재접속·세션 종료 뒤 오래된 콜백이 새 세션을 변경하지 못하게 함 |
| task_id | "명함을 확인하고 저장" 같은 사용자 목적의 수명. 앱이 발급 |
| revision | 이름·수신자·문구·대상 사진 등 의미 있는 변경마다 증가 |
| operation_id | 목적을 수행하는 개별 촬영/조회/저장 시도. 앱이 발급 |
| tool_call_id | Gemini 프로토콜의 호출/응답 대응. task_id와 분리 |
| artifact_id | 특정 촬영 사진·조회 결과. task_id와 revision 및 시각을 기록 |
| idempotency_key | 서버 쓰기 재시도 중복 방지. 서버 지원이 있을 때 효과를 보장 |

작업 상태: queued / running / waiting_dependency / waiting_user / held / completed / failed / cancelled / outcome_unknown.

cancel_requested는 취소 요청을 보낸 상태이며 cancelled와 다르다. 실제 연산이 끝났는지와 그 결과를 현재 대화에 사용해도 되는지를 따로 기록한다. 이미 완료된 외부 변경은 뒤늦은 취소로 cancelled로 바꾸지 않는다.

승인은 작업 번호만이 아니라 revision과 실행 내용(대상·수신자·문구·사진)에 묶는다. 내용이 바뀌면 그 내용에 대한 기존 승인은 유효하지 않다. 이는 기존 기능의 승인 정책을 구현하는 것으로 모든 읽기 동작에 승인을 추가하는 의미가 아니다.

## Gemini에 제공할 정보와 도구 계약

세션 지침에 동작 원칙을 넣고 도구 결과에 작은 작업 상태 스냅샷을 함께 반환한다. 원본 사진이나 전체 DB 결과를 매번 반복하지 않는다.

예시 상태:

```json
{
  "state_version": 18,
  "focus_task_id": "T42",
  "tasks": [
    {"task_id":"T41","revision":1,"goal":"명함 촬영","status":"running","cancelability":"best_effort"},
    {"task_id":"T42","revision":2,"goal":"김민수 검색","status":"waiting_user","waiting_for":"동명이인 선택"}
  ]
}
```

기존 업무 도구를 유지하되 실행 문맥에 task_id/revision을 연결한다. 첫 도구는 앱에서 새 작업을 발급하고 결과로 ID를 반환한다. 관계가 불명확한 후속 도구를 앱이 임의로 현재 작업에 붙이지 않는다.

제안하는 제어 기능:

- `get_task_state`: 진행·완료·확인 대기 상태 조회.
- `update_task`: 대상 task_id와 expected_revision에 대해 cancel / hold / resume / replace 요청. replace는 변경 내용과 기존 작업의 처리 의도를 포함.
- 기존 업무 도구: 새 작업 또는 기존 작업의 후속 operation 시작. 의존 결과는 artifact_id로 참조.

한 사용자 발화가 "A는 취소하고 B를 시작"이면 취소/대체 의도를 앱이 먼저 반영한 다음 B의 실행 가능성을 검사한다. 대체 요청이 실패해도 이미 반영한 외부 쓰기를 되돌렸다고 가정하지 않는다. 같은 배치의 도구를 무조건 병렬 실행하지 않는다.

잘못된 task_id, 예전 revision, 없는 artifact는 실행하지 않고 현재 상태와 함께 재판단을 요청한다. 재판단을 무한 반복하지 않고 상태 갱신 후에도 해결되지 않는 대상 모호성만 사용자에게 묻는다. 모델이 자체 보고한 confidence 숫자만으로 외부 변경을 허용하지 않는다.

## 도구 이름 대신 공통 속성으로 실행 정책 정의

각 도구는 다음 메타데이터를 등록한다. 새 기능은 이 속성과 어댑터를 제공하면 공통 규칙을 따른다.

| 속성 | 예 |
|---|---|
| effect | read / local_capture / external_write / ongoing_recording |
| resource | camera / microphone / contact_ui / network 및 필요 시 특정 대상 |
| cancelability | cooperative / best_effort / not_after_dispatch |
| retryability | safe / server_idempotent / reconcile_first / never |
| prerequisites | 특정 operation 완료, artifact 존재, 기존 기능의 승인 |
| timeout | 도구별 실행·확인 시간 제한 |
| reporting | foreground / deferred / silent |

- 카메라 중복 촬영은 직렬화한다. 시작한 물리 촬영이 아직 끝나지 않았으면 논리적 취소만으로 카메라 점유를 해제하지 않는다.
- 서로 독립적인 조회와 촬영은 자원·의존성·사용자 의도가 허용하면 병행한다.
- 동일 수신자 전송이나 같은 레코드 변경은 개별 자원 키와 실행 키로 충돌을 막는다.
- 회의 녹음처럼 지속되는 작업은 화제 전환으로 종료하지 않는다. 현재 앱은 회의 녹음 중 Live 세션을 종료하므로 동시 대화는 별도 지원 검증 전까지 허용하지 않는다.

## 새 발화 처리

1. 음성 interruption은 우선 답변 재생을 중단한다. 업무 취소로 해석하지 않는다.
2. 영향받을 수 있는 미실행 외부 변경과 후속 단계를 잠시 held로 둔다. 모든 작업·모든 읽기 요청을 전역 취소하지 않는다. 이미 전송된 쓰기는 실행 상태를 확인한다.
3. Gemini가 새 발화를 활성 작업 상태와 함께 해석한다.
4. 앱이 task_id/revision/승인/자원/의존성을 검사하고 변경을 반영한다.
5. 읽기·촬영이 뒤늦게 끝나면 원래 작업의 결과로 등록한다. 취소되거나 대체된 작업의 결과는 새 작업으로 자동 전달하지 않는다.
6. 사용자 관심 작업의 결과를 먼저 말하고, 유지 중인 다른 작업 결과는 적절한 시점에 짧게 알린다.

응답 생성 중단, 도구 프로토콜 취소, 사용자 목적 취소는 서로 다른 이벤트다. Gemini의 toolCallCancellation이 오면 해당 호출의 응답 연결을 끝내고 가능한 실행을 중단/보류하되 사용자 목적 전체가 취소됐다고 단정하지 않는다. 프로토콜에서 취소된 tool_call_id에 뒤늦은 성공 응답을 보내지 않는다. 결과는 앱 작업 저장소에서 보관·조회하며 재개는 새 유효 호출과 현재 revision을 통해 진행한다.

## 상황별 정책

| 상황 | 판단 및 처리 |
|---|---|
| "사진 말고 사람 찾아" | 기존 촬영 목적 대체. 가능한 촬영 중단, 늦은 사진 결과 격리, 검색 시작 |
| "찍어두고 사람도 찾아" | 촬영 유지, 독립 검색 추가, 결과를 각 작업에 연결 |
| "그 사진으로 검색해" | 사진 artifact를 의존 대상으로 지정, 완료 전 검색 대기 |
| "김민수 말고 김민준" | 검색 조건 revision 증가, 옛 결과 선택/실행 금지 |
| "얼마나 걸려?" | 작업 상태 조회, 기존 작업 유지 |
| "응" | 현재 확인 대상이 하나이고 내용이 변하지 않았을 때만 그 대상에 적용. 여러 개면 대상 확인 |
| "잠깐" | 재생 중단 및 영향받는 후속 단계 보류. 녹음 등 독립 지속 작업은 자동 종료하지 않음 |
| "아까 하던 거 계속" | 대상과 재개 가능 단계 확인. 완료된 쓰기를 다시 실행하지 않음 |
| "찍지 마"가 셔터 직후 도착 | 실제 촬영 완료 사실과 후속 사용 중단을 구분해 보고 |
| 저장 중 연결 끊김 | outcome_unknown. 서버 조회/실행 키로 확인 전 재전송 금지 |
| 두 작업이 같은 카메라 필요 | 직렬 대기, 동일 요청 중복이면 기존 operation 반환 |
| 사진 촬영 실패 | 요청에 맞는 대체 수단만 사용. 명시적 취소를 촬영 실패로 바꾸어 영상 프레임을 대신 보내지 않음 |
| 작업 일부 성공 | 성공한 단계 보존, 실패/미확정 단계만 처리. 전체 성공 또는 전체 취소로 표시하지 않음 |
| 세션 재접속 | 작업 상태 요약 복원, 외부 실행 중/미확정 작업 확인. 이전 세션 콜백 차단 |
| 작업 실행을 요구하지 않는 일반 대화 | 관심 대화만 전환, 유지한 업무는 그대로. 불필요한 취소 확인 질문 금지 |

## 현재 Flash Live 모델의 제약

현재 GeminiConfig.MODEL은 gemini-3.1-flash-live-preview이고 도구 선언은 BLOCKING이다. 공식 capabilities 문서의 해당 모델 열은 비동기 function calling을 지원하지 않으며 도구 응답 전까지 모델 응답을 기다린다고 설명한다. 따라서 모든 도구에 NON_BLOCKING을 붙이는 방식은 채택하지 않는다.

제안: 긴 도구를 앱 작업 접수로 전환해 `accepted`, task_id, operation_id를 빠르게 반환한다. 이 응답은 완료를 뜻하지 않는다. 실제 작업은 앱에서 실행하고 get_task_state로 결과를 조회한다. 도구 결과 대기를 반복하는 모델 폴링 루프를 만들지 않는다. 화면에는 즉시 상태를 갱신하되 완료 음성 알림은 사용자 발화·모델 응답과 충돌하지 않는 시점에 전달한다. 현재 프로토콜에서 백그라운드 완료를 자연스럽게 알리는 방식은 별도 통합 테스트가 필요하며, 재생 중 clientContent(turnComplete=true)를 임의로 보내 응답을 끊는 방식은 피한다.

향후 지원 모델에서 비동기 도구를 도입해도 앱의 작업 상태와 실행 정책은 동일하게 유지한다. 이번 설계를 위해 모델 교체를 전제하지 않는다.

근거: https://ai.google.dev/gemini-api/docs/live-api/capabilities (2026-09-19 확인).

## 현재 코드에서 먼저 보강할 지점

1. ToolCallRouter의 call_id → Job 구조 옆에 task/operation 레지스트리 추가. 실행 전과 결과 전달 직전에 유효성 검사. 취소·예외·중복 호출 모두 finally 정리와 일관된 상태 전이 적용.
2. StreamViewModel.captureFreshVisualFrame의 CancellationException 재전파. 캡처 실패 fallback과 사용자 취소를 구분하고 실제 사진 요청 중단 지원 여부 확인.
3. OpenClawBridge의 HTTP 요청을 취소 가능한 호출과 연결. 외부 쓰기는 요청 전/전송 후/응답 확인 상태를 구분. 클라이언트 취소를 서버 rollback으로 표현하지 않음.
4. capture_current_view 결과를 artifact로 고정. 현재 save_life_memory는 승인 시 다시 촬영하므로, 사용자가 확인한 장면과 저장된 장면이 달라질 수 있다. 저장은 승인된 작업 revision의 artifact를 사용.
5. 공유 lastToolCallStatus 대신 작업별 상태 보관. 오래된 조회 완료가 현재 검색의 화면 상태를 덮어쓰지 못하게 함.
6. 세션 재접속 시 필요한 미완료/미확정 외부 작업 메타데이터 유지. 영구 보관할 사진과 일시적인 캡처의 수명은 별도 정책으로 정의.

## 검증

순수 상태 머신 테스트와 실제 어댑터 테스트를 나눈다. 가짜 카메라와 가짜 서버로 완료·취소·시간 초과 순서를 제어한다.

필수 회귀 시나리오:

- 취소 직전/직후 사진 완료, 원래 사진이 새 요청에 전송되지 않음.
- revision 1 검색 결과가 revision 2보다 늦게 도착해도 현재 상태를 덮어쓰지 않음.
- 요청 중복 수신과 재접속 시 외부 쓰기가 중복 실행되지 않음. 서버 실행 키 미지원이면 미확정 상태 유지.
- "사진은 계속"과 toolCallCancellation 동시 도착 시 목적 유지와 프로토콜 취소가 구분됨.
- 승인 후 수신자/사진/문구가 바뀌면 이전 승인으로 실행되지 않음.
- 여러 확인 대기 작업 중 "응"이 잘못된 작업을 승인하지 않음.
- 쓰기 완료 후 취소 요청에 거짓 cancelled를 반환하지 않음.
- 녹음 유지 요청과 일반 대화가 전체 취소로 처리되지 않음.
- 외부 쓰기 직전 held 및 revision 검사를 통과한 작업만 실행됨.
- 취소된 프로토콜 호출에 뒤늦은 도구 응답을 보내지 않음.

Gemini 판단은 동일한 한국어 대화 사례를 반복 평가한다. 정정/추가/상태 질문/부정/지시대명사 해석, 불필요한 확인 질문 비율, 잘못된 작업 변경 비율을 측정한다. 모델 테스트와 별개로 앱의 상태 불변식은 항상 만족해야 한다.
